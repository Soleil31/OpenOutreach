# Автопочинка

Смена вёрстки на стороне LinkedIn больше не должна останавливать аутрич на
недели. 10 августа 2026 года аккаунт потерял сессию, поломку заметили 24-го —
за это время демон сделал ~1300 попыток входа и сжёг ~105 000 задач.

## Как это устроено

```
детектор → хилер → верификатор → шиппер → наблюдение → (откат)
```

| Шаг | Файл | Что делает |
|---|---|---|
| Детектор | `detect.py` | читает состояние аккаунта и пакеты улик, называет класс поломки |
| Хилер | `heal.py` | просит у модели новый слой селекторов по строгой схеме |
| Верификатор | `verify.py` | проверяет патч на сохранённых страницах без обращений к LinkedIn |
| Шиппер | `ship.py` | коммит в `main` → выкатка → наблюдение → откат |
| Журнал | `incidents.py` | вся история инцидента в файлах, читаемых глазами |
| Уведомления | `notify.py` | пишет в файл, который читает хостовый мониторинг |

## Два правила, на которых всё держится

**Автопочинка запускается только при смене вёрстки.** Проверка личности,
капча и отклонённый пароль — это не поломка кода. Чинить их патчем означает
продолжать автоматические действия против площадки, которая уже выразила
недоверие, и потерять аккаунт окончательно. Такие случаи паркуют демона и зовут
человека.

**Право записи выдано на один файл**, `linkedin/browser/selectors.py`. Патч,
затрагивающий что-либо ещё, отклоняется без разбора содержания. Агент, свободно
правящий код аутрича, однажды изменит логику отправки сообщений живым людям.

## Запуск

```bash
python -m tools.autoheal.run --repo /path/to/OpenOutreach            # полный цикл
python -m tools.autoheal.run --repo /path/to/OpenOutreach --dry-run  # до вердикта, без выкатки
python -m tools.autoheal.run --status                                # что происходит
```

## Параметры

Все значения меняются переменными окружения, править код не нужно —
`python -m tools.autoheal.config` покажет действующие.

| Что | По умолчанию | Почему так |
|---|---|---|
| Попыток на инцидент | 3 | больше — это уже «задача не по силам», а не «модель ошиблась» |
| Выкаток в сутки | 2 | защита от петли, в которой модуль чинит собственную поломку |
| Наблюдение | 20 мин | несколько полных циклов задач |
| Успешных действий для успеха | 1 | доказывает, что работает вся цепочка |
| Ночные выкатки | запрещены | откат автоматический, а последствия видит человек |
| Обращений к модели | 4 | считаем вызовы, а не токены: шлюз расход не возвращает |
| Серверы | `Owlgram2` | расширять список — сознательное решение |

## Что он сделал за первые две недели: ничего

С 31.08 по 16.09.2026 — 697 инцидентов, у всех причина `unknown`, все «требует
человека», ни одной попытки патча и ни одного обращения к модели. Это не сбой:
чинить кодом разрешён единственный класс, `locator_break`, а LinkedIn за это
время вёрстку не менял. Падало другое — 367 раз след сломанного сторожа
браузера (`'NoneType' … wait_for_load_state`), 92 упора в лимит потоков, 89
таймаутов, 30 `Target crashed`.

Из этого сделаны три вывода, 16.09.2026:

1. **Смерть браузера — не наш класс.** `MONITORED_REASONS` теперь отсекает её до
   заведения инцидента: за ней и так следят deadman, самоперезапуск демона и
   состояние аккаунта. Дублировать чужую работу шумом — значит приучить читать
   алерты по диагонали.
2. **«Требует человека» — не «закрыто».** `find_open()` считал это состояние
   закрытым, поэтому дедуп не срабатывал и каждый прогон крона заводил инцидент
   заново. Отсюда 697 каталогов и 159 МБ на горстку реальных поломок. Теперь
   повтор ложится в тот же инцидент счётчиком `repeats`, а человека зовут один
   раз.
3. **Журнал — для чтения, а не архив.** `incidents.prune()` держит последние
   `KEEP_INCIDENTS` и всё моложе `KEEP_INCIDENT_DAYS`.

Молчание модуля — штатное состояние. Он страховка на случай смены вёрстки, а не
дежурный по всем поломкам.

## Черновой разбор (diagnose.py)

Там, где чинить нечем, модуль всё равно может прочитать улики за человека.
Для классов из `DIAGNOSABLE_REASONS` (`wedge`, `unknown`) он кладёт в инцидент
`diagnosis.md` — гипотезу, цитаты из улик, чем проверить — и, если правка
очевидна, `suggested.patch`. Гипотеза едет в уведомление, а не остаётся лежать
на диске.

**Патч не применяется никогда.** Разница между разбором и починкой — оракул.
У селекторов он есть: верификатор гоняет кандидата на корпусе сохранённых
страниц и умеет сказать «нет». У зависшего демона оракула нет, и «модель
предложила — машина выкатила» здесь означало бы выкатывать непроверенное в
переписку с живыми людьми.

Материал для разбора появился 16.09.2026 вместе со сторожем: он пишет в дамп
стеки **всех** потоков и счётчики контейнера. До этого на зависании улик не было
вовсе — дамп страницы бесполезен, когда браузер цел, а висит Python.

## Чего модуль не делает

Не обходит капчу и проверки личности. Не проходит двухфакторную аутентификацию.
Не заводит и не меняет аккаунты. Не трогает прокси, лимиты и расписание. Не
правит миграции и схему базы. Не меняет тексты сообщений и правила квалификации.

## Успех — это действия, а не тишина

После выкатки успехом считается появление настоящих действий в
`linkedin_actionlog`. «Ошибка перестала сыпаться» успехом не считается: молчать
умеет и мёртвый демон — именно так двухнедельный простой и выглядел здоровым в
ежедневном отчёте.

## Верификатор обязан уметь сказать «нет»

Перед тем как доверять зелёному вердикту, `verify.self_check()` подсовывает
заведомо сломанные селекторы и требует красного. Проверка не формальная: при
первой сборке верификатор выдал зелёный на сломанном коде, потому что образцы
корпуса не были самодостаточны — внешние стили LinkedIn не грузились, и обе
копии формы читались как видимые. Подробности — в
`tools/selector_verifier/README.md`.
